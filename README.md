## Hardware requirements

- A Game Boy Color with an infrared window. The GBA has no infrared, not even in GBC mode.
- A cartridge or flashcart with the MBC5 mapper and saveable SRAM. Recordings live in the SRAM, not in RAM. The more SRAM there is, the more signals fit: 30 with 128 KB, 15 with 64 KB, 7 with 32 KB, 1 with 8 KB.
- The ROM is GBC only (`rgbfix -C`): it does not start on a DMG.

## How to use it

On the **first launch**, with no card, the program goes straight to reception. Point the remote at the Game Boy and press one of its buttons. When the signal is captured the program asks for the **card name first, then the signal name**. The signal is saved in the card just created and you land on the card list.

The first screen is always the card list, and it is never empty: while no card exists, every cancellation, error or discard goes back to reception. The same happens if you delete the last card.

| Screen | Key | Action |
|---|---|---|
| Card list | Up / Down | Choose the card (the list scrolls) |
| Card list | **A** | Open the card and show its signals |
| Card list | **START = New** | Create a card: asks for the name, the card starts empty |
| Card list | **SELECT = Del** | Delete the card, with two confirmations |
| Signal list | Up / Down | Choose the signal |
| Signal list | **A = OK** | Send the selected signal |
| Signal list | **START = New** | Record a new signal in the card: reception, then name |
| Signal list | **SELECT = Del** | Ask for confirmation and delete the signal |
| Signal list | **B = Back** | Go back to the card list |
| Reception | **B = Back** | Cancel the wait. With no card, reception starts again |
| Keyboard | D-pad | Move the cursor |
| Keyboard | A | Type the character |
| Keyboard | **B = Back** | Erase the last character. With an empty name, discard everything and go back (to reception if there is no card) |
| Keyboard | START | Save with the typed name. With an empty name, ask to confirm the cancellation |
| Cancellation confirmation | **A = YES** | Discard and go back |
| Cancellation confirmation | **B = NO** | Back to the keyboard |
| Signal deletion | **A = YES / B = NO** | Delete / cancel |
| Card deletion, first warning | **A = CONTINUE / B = CANCEL** | Continue / cancel |
| Card deletion, second confirmation | **A = YES / B = NO** | Delete the card and all its signals / cancel |
| Error | A | Close the screen |

Every screen shows a small legend of the available keys at the bottom.

**Deleting a card:** two warnings appear one after the other. The first says that deleting the card also deletes all its signals. The second asks for a second confirmation. The card disappears only if you confirm both.

**Empty card:** a card with no signals stays in the list. Inside you see `EMPTY CARD`, and START adds a signal.

**Names:**
- At most 11 characters, for both cards and signals.
- Available characters: `A-Z`, `0-9`, `-`, `.`, `:` and space. The keyboard is QWERTY, with the number row above the letters.
- At least one character that is not a space (E04 for a name of spaces only).
- Card names are unique among cards. Signal names are unique inside their card (E05 or E13 if already used).

**Sounds:** a short melody when a recording succeeds, and another short descending melody when you delete a signal or a card.

**Capacity:** at most 32 cards and 8 signals per card. The total number of signals depends on the card's SRAM, which the program measures at every boot: `2 × banks − 1`, at most 30. With 128 KB (16 banks) that is 30 signals, with 32 KB (4 banks) it is 7, with 8 KB (1 bank) it is 1. The signals of all cards share the same pool. The card list shows `SIGNALS 03/30`: signals in use and the maximum the SRAM allows.

The development rules (required behavior, conventions, verification) are in `../AGENTS.md`.

## Errors

Errors show `ERROR Enn` on screen (and, for names, under the name field), with a message in words and the pointer `SEE TECHNICAL.MD`. Cancelling with B is not an error and shows no code.

The **table of codes**, with the meaning and what to do, is in [`docs/TECHNICAL.md`](docs/TECHNICAL.md), section 7. On the E01, E08 and E11 screens two SRAM lines also appear (`SRAM BANKS`, `SRAM KEPT`): they are explained in section 7.3.

## From the code to the console

The **only file you need on the console is the ROM `build/gbc-remote.gbc`** (or a variant in a subfolder of `build/`). You do not need `.sym`, `.map`, `.o`, the tests or the venv: those are development files. The flashcart creates the save file, you do not bring it.

Menus and settings change from flashcart to flashcart: for those steps the manufacturer's manual applies. This procedure was partly verified on an EverDrive GB card (see "What we discovered").

### What you need

- A PC with Linux, macOS or Windows, `make`, and RGBDS 1.0 or later.
- A flashcart for the Game Boy Color with the MBC5 mapper and saveable SRAM, and its microSD.
- A Game Boy Color. The GBA has no infrared, the DMG does not start GBC-only ROMs.
- An infrared remote to record.

### 1. Install RGBDS

On Linux:

```
curl -L -O https://github.com/gbdev/rgbds/releases/download/v1.0.4/rgbds-linux-x86_64.tar.xz
mkdir rgbds
tar -xJf rgbds-linux-x86_64.tar.xz -C rgbds
cd rgbds
sudo ./install.sh
rgbasm --version
```

The last command must print `rgbasm v1.0.4` (or newer). On macOS and Windows download the archive of the same release from the [RGBDS releases](https://github.com/gbdev/rgbds/releases) page and put `rgbasm`, `rgblink` and `rgbfix` in the `PATH`. Without `sudo` you can leave RGBDS where you extracted it and pass its path to `make`.

### 2. Build the ROM

From the `GBC-remote/` folder:

```
make
```

If RGBDS is not in the `PATH`: `make RGBDS_DIR=/path/to/rgbds/` (with the trailing slash). The result is `build/gbc-remote.gbc`, 32 KB, with the header declaring 128 KB of SRAM.

The program measures the SRAM it finds and adapts the capacity, but some flashcarts decide the SRAM from the header. If yours has less than 128 KB, try a variant with the matching header:

| SRAM | Command | ROM |
|---|---|---|
| 128 KB (default) | `make` | `build/gbc-remote.gbc` |
| 64 KB | `make SRAM_KB=64` | `build/sram-64kb/gbc-remote.gbc` |
| 32 KB | `make SRAM_KB=32` | `build/sram-32kb/gbc-remote.gbc` |
| 8 KB | `make SRAM_KB=8` | `build/sram-8kb/gbc-remote.gbc` |

`SRAM_KB` also sets a ceiling on the banks the program may use, so a small memory can be simulated on the emulator. Optional: `make test` (see the Tests section).

### 3. Prepare the microSD

1. Format the microSD as the flashcart requires (usually FAT32).
2. Copy the ROM to the card, in the games folder.
3. Eject the microSD safely and put it back in the flashcart.

### 4. Power on and use

1. With the console **off**, insert the flashcart.
2. Power on the Game Boy Color and choose `GBCREMOTE` in the flashcart menu.
3. On the first launch you see `WAITING FOR SIGNAL`. Point the remote at the infrared window (top edge of the Game Boy Color), a few centimeters away, and press one of its buttons.
4. Type the card name and press START, then the signal name and START again. You hear the confirmation melody and see the card list.
5. Open the card with A. In the signal list, A sends the signal: point the Game Boy at the device to control.

On the card list, at the top, `SIGNALS 03/30` shows how many signals are in use and the maximum the SRAM found allows.

### 5. Saving data with an EverDrive GB card

If your flashcart uses the Krikzz EverDrive GB system (the menu screen or the `GBOS.GB` file tell you), the menu has, when you press B on the chosen game, these entries: `Load And Start`, `Load Only`, `RAM Size:`, `Save RAM:`, `Copy File To SRAM`, `Copy SRAM To File`. Saves are `.srm` files in `/EDGB/SAVE` on the microSD.

Recommended procedure (the entries are deduced from the system's strings, not from a manual):

1. On the chosen game press B and set `RAM Size` to match the ROM header (32K for the 32 KB variant) and turn `Save RAM` on.
2. Start with `Load And Start`, use the program, **wait at least 3 seconds**, and power off.
3. At the next power-on, in the menu, choose `GBCREMOTE`, press B and choose **`Copy SRAM To File`**: it copies the SRAM the card kept into the `.srm`.
4. Then `Load And Start`.

If you skip step 3, `Load And Start` reloads the old `.srm` and the new data is lost. To start from scratch, delete `/EDGB/SAVE/gbc-remote.srm`.

### 6. If something goes wrong

- **Black screen:** check that it is a Game Boy Color, not a DMG.
- **`ERROR E01` or `ERROR E11`:** the write to the SRAM is not read back the same: the flashcart has no SRAM or has the SRAM disabled.
- **`ERROR E03` on every recording:** signal too short. Move the remote closer and avoid sunlight and incandescent lamps.
- **`ERROR E08`:** the directory was damaged and held cards, and it is reformatted. The `SRAM BANKS` and `SRAM KEPT` lines under the code tell you the state of the SRAM (see `docs/TECHNICAL.md`, section 7.3). See also step 5.
- **Data disappears after a power-off:** check step 5. To know how much SRAM there is and whether it is kept, use the diagnostic, or the debug build and the event log.
- **The recorded signal does nothing when you send it:** record with the remote close. Infrared uses double speed (the default): do not change it.
- **Few signals:** the limit depends on the card's SRAM (`SIGNALS 03/07` means 7 places).

## SRAM diagnostic

It shows how many SRAM banks there are and whether they are kept after a power-off.

**Just see the capacity** (nothing is erased): hold **SELECT** while you start the ROM. In the menu you read `SRAM BANKS: NN/16` (the distinct banks) and `SRAM KEPT: YES/NO`. Press **B** to leave.

**Test whether the data is kept** (this erases every saved command):

1. Hold SELECT at boot, then press **A**: it writes a pattern in each of the 16 banks and reads it back. You see `BANK 00 OK` ... `BANK 15 OK`.
2. Power off, power on holding SELECT, and press **START** to check the same pattern.
3. **B** to leave. The program starts again from scratch.

| Result | Meaning |
|---|---|
| All OK after A and after START | The SRAM works and is kept. |
| BAD right after A on some banks | The SRAM has fewer than 16 distinct banks. This is normal with 32 KB or 8 KB: those banks overlap. |
| OK after A, BAD after START | The flashcart does not keep (or does not restore) the SRAM between boots. |

## Debug build and event log

`make DEBUG=1` builds `build/debug/gbc-remote.gbc` with a debug screen, opened with B on the card list. It shows the boot counter, the CPU speed, the SRAM banks and whether the SRAM was kept, the signals, cards and directory bytes in use, the state of both directory copies at mount, the last error, and the signals of every card.

Every ROM (debug or normal) also keeps an **event log** in the SRAM: boots, probe results, directory mounts, errors, and saves. `python3 tools/decode_log.py gbc-remote.srm` decodes it on the PC. If after a power-off the log still holds the entries of the previous boot, the SRAM was kept.

Everything is explained in [`docs/DEBUG.md`](docs/DEBUG.md).

## What we discovered

A summary of what we learned about the hardware. The details, the figures and the status of each fact are in [`docs/TECHNICAL.md`](docs/TECHNICAL.md).

- **The infrared signal must last at least a full frame.** The first version recorded only 35 ms and the command was not recognized. It now records 119 ms and replay works on a console.
- **The card's SRAM is smaller than expected.** With the 128 KB header the banks overlapped, that is the signals landed on the same memory and the program overwrote its own data. The card used has 32 KB (4 banks), that is 7 signals. The doubt and how we measure it are explained in section 4.7 of `docs/TECHNICAL.md`.
- **The card is a Krikzz EverDrive GB.** It saves in `/EDGB/SAVE/*.srm`, but only by its own rules (file menu, `Copy SRAM To File`).
- **The extracted save was old and had one wrong bit** in the directory. That is why the directory now has two copies and a check, and a single wrong bit is repaired on its own.
- **We do not know yet whether the data survives a power-off** with the procedure of step 5: it has to be tried. The event log is built to answer this.

## Hardware used for testing

So far **a single flashcart** has been tried: a card sold as "Game Flash GB PRO (Bitfunx), OS V4", with "EverDrive GB MAX" written on it and the Krikzz EverDrive GB system. With the 128 KB header the SRAM shows as overlapping, with the 32 KB header it shows 4 banks. The full list (console, emulator, tools, results) is in `docs/TECHNICAL.md`, section 14.

## Tests

```
python3 -m venv .venv
.venv/bin/pip install -r tests/requirements.txt
make test
make coverage
```

The suite has 50 unit tests (a test ROM with the real routines), 19 flow scenarios (the real ROM with keys pressed and the screen read), 4 flow scenarios on the debug build, 4 SRAM size checks (8, 32, 64 and 128 KB), and 7 tests of the log decoder. They run on the PyBoy emulator without a window. Infrared is simulated. `make coverage` measures how many labels of the code the tests reach and regenerates the badges at the top of this file. The details are in `docs/TECHNICAL.md`.

## Status

The cards feature, the debug build, the event log and the messages in words are implemented, and every test passes on the emulator (50 unit tests, 19 flow scenarios, 4 debug scenarios, 4 size checks, 7 tool tests). On a real console, before the cards feature, recording, naming and replay worked. With the cards feature: no error at boot. Persistence after a power-off is **not verified yet**, and the new features have not been tried on a console.
